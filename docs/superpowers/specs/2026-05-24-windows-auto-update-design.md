# Windows 桌面版更新能力设计

## 背景

A 股策略回测工作台当前已经能构建 Windows NSIS 安装包，并计划通过 `dzc-bit/A_stock_receiver` GitHub 仓库维护发布版本。用户希望已经安装桌面应用的人也能获得后续更新，而不是每次手动寻找新版安装包。

本设计只覆盖 Windows 桌面版更新能力。移动端、macOS、Linux、自建更新服务器和自动交易功能不在本轮范围内。

## 目标

- 已安装 Windows 用户可以在应用内检查并安装新版本。
- 发布渠道使用 GitHub Releases，避免额外维护更新服务器。
- 更新包必须签名，私钥不进入仓库。
- 更新体验全中文，和现有桌面界面风格一致。
- 发布流程可文档化，后续可以迁移到 GitHub Actions 自动发布。

## 非目标

- 不做应用商店发布。
- 不做后台强制静默安装。
- 不做复杂的版本分支、灰度发布或多渠道发布。
- 不在代码仓库提交更新签名私钥。

## 推荐方案

使用 Tauri v2 官方 updater 插件，更新文件托管在 GitHub Releases。

选择这个方案的原因：

- 它直接服务于“已安装用户能更新”的目标。
- 与当前 Tauri v2 + NSIS Windows 打包方式匹配。
- GitHub Releases 足够满足当前分发规模。
- Tauri updater 自带签名校验，能避免用户安装被篡改的更新包。

## 用户体验

应用界面新增一个中文更新入口，建议放在顶部工具区或设置区域：

- 默认显示当前版本。
- 用户点击“检查更新”后，应用请求更新端点。
- 如果没有新版本，提示“当前已是最新版本”。
- 如果有新版本，显示版本号、发布日期和简短更新说明。
- 用户确认后下载更新。
- 下载完成后显示“安装并重启”。
- 如果网络异常、更新配置错误、签名不匹配或安装失败，显示明确中文错误提示，并保留“稍后重试”。

MVP 阶段采用手动检查更新。启动时自动检查可以作为后续增强，避免第一次实现时增加打扰和误报。

## 发布数据流

1. 开发者更新应用版本号。
2. 构建 Windows NSIS 安装包和 Tauri updater 需要的更新资产。
3. 构建过程使用私钥签名更新资产。
4. 发布资产上传到 `dzc-bit/A_stock_receiver` 的 GitHub Release。
5. 应用内 updater 使用配置好的 GitHub Release 端点检查新版本。
6. Tauri 校验更新签名。
7. 用户确认后安装更新并重启应用。

## 组件变更

### Tauri 后端配置

- 添加 Tauri updater 插件依赖。
- 在 `src-tauri/tauri.conf.json` 配置 updater endpoint 和公钥。
- 保持当前 Windows NSIS 打包目标。
- 将签名私钥配置为环境变量或 GitHub Actions secret，不写入仓库。

### 前端界面

- 添加更新状态 UI，文案全部中文。
- 添加“检查更新”按钮。
- 将 updater 状态抽成前端模块，避免更新逻辑散落在主界面组件中。
- 错误提示面向普通用户，不暴露过多底层堆栈。

### 发布文档

新增或扩展发布文档，说明：

- 如何生成 updater signing key。
- 哪些环境变量必须配置。
- 如何提升版本号。
- 如何构建 Windows 安装包。
- 如何创建 GitHub Release 并上传资产。
- 已安装用户如何触发更新。

## 错误处理

- 网络不可用：提示网络连接失败，可稍后重试。
- 无新版本：提示当前已是最新版本。
- 更新端点不可达：提示更新服务暂时不可用。
- 签名校验失败：阻止安装，提示更新文件校验失败。
- 下载中断：允许重新检查并重新下载。
- 安装失败：提示用户重新下载新版安装包或稍后重试。

## 安全要求

- 私钥不能提交到 git。
- 公钥可以提交到 `tauri.conf.json`。
- GitHub Actions 中使用 repository secrets 保存签名私钥和私钥密码。
- 发布文档明确提醒不要将 `.key`、`.pem`、私钥文本和 secret 输出写入日志或提交。

## 测试与验证

实现完成后需要验证：

- 前端更新 UI 的状态渲染和错误状态测试通过。
- `npm run test:ui -- --run` 通过。
- `npm run build` 通过。
- `npm run tauri -- build --debug` 能继续生成 Windows NSIS 安装包。
- 更新配置不会破坏现有启动和打包。

真实跨版本自更新需要两个带签名的 Release 版本才能完整端到端验证。本轮实现完成时，至少要保证本地构建、配置和 UI 流程可用，并在文档中写明真实发布验证步骤。
